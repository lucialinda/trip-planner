# commit

Git 커밋 메시지를 일관된 컨벤션 형식으로 작성하고 커밋하기 위한 스킬.

## 워크플로

1. **변경사항 확인** — `git status`와 `git diff`(또는 `git diff --staged`)로 무엇이 바뀌었는지 직접 본다. 메시지를 잘 쓰려면 디프를 먼저 봐야 한다.
2. **stage 범위 판단** — 사용자가 별도로 지정하지 않았다면, **이번 대화에서 다룬 변경분만** stage 한다. 작업 트리에 무관한 다른 modified 파일이 섞여 있으면 그건 그대로 두고, 필요하면 사용자에게 어떻게 처리할지 짧게 묻는다.
3. **type/scope 결정** — 디프 내용을 보고 아래 표에서 가장 적합한 type을 고른다. scope은 영향 범위(파일/모듈/도메인)를 짧게 한 단어로.
4. **설명 작성** — 50자 이내, 한글 또는 영문, 명령형/현재형. 마침표 ❌. "왜 그렇게 고쳤는지"가 코드만 봐서는 안 드러나면 1~3줄짜리 body를 덧붙인다.
5. **복합 변경이면 type을 쉼표로 결합**하고, body에 type별로 한 줄씩 항목을 적는다 (아래 "복합 type" 참고).
6. **커밋 실행** — 메시지가 정해지면 `git commit -m "..."`으로 바로 커밋한다. 사용자가 메시지를 미리 보고 싶다고 했거나, 변경 범위가 모호하면 커밋 직전에 한 줄로 메시지를 보여주고 확인받는다.

## 메시지 포맷

```
type(scope): 설명
```

| 요소 | 필수 여부 | 설명 |
|------|-----------|------|
| **type** | required | 변경 유형 (아래 type 목록 참고) |
| **scope** | optional | 변경 영향 범위 — 파일·모듈·도메인 한 단어 (예: `yml`, `network`, `storage`, `auth`, `dropdown-menu`) |
| **설명** | required | 50자 이내 한글/영문, 명령형, 마침표 없음 |

## Type 목록

- `feat` — 새 기능
- `fix` — 버그 수정
- `docs` — 문서 변경
- `style` — 코드 스타일 (동작 변경 없음, 포매팅·세미콜론 등)
- `refactor` — 리팩토링 (동작은 그대로, 구조만 정리)
- `test` — 테스트 추가/수정
- `chore` — 빌드, 설정, 의존성 등 기타
- `ci` — CI/CD 변경
- `perf` — 성능 개선

복합 변경(한 커밋이 두 type에 걸칠 때)은 쉼표로 결합: `fix,feat`, `refactor,docs` 등. 단, 가능하면 커밋을 분리하는 편이 깔끔하다.

## 복합 type일 때의 body 규칙

복합 type을 쓰면 body에 각 type별로 한 줄씩 항목을 적어 어느 변경이 어디 속하는지 분명하게 한다.

```
fix,feat(auth): 로그인 흐름 정비

- fix: 만료 토큰 재발급 시 무한 루프 발생하던 문제 수정
- feat: 소셜 로그인 (Kakao) 추가
```

단일 type일 때 body는 보통 생략한다. 단, "왜"가 코드/디프에서 안 드러나면 짧게 적어둔다.

## 예시

**Example 1 — 단일 fix:**
```
fix(dropdown-menu): 트리거 너비에 묶이는 문제 해결
```

**Example 2 — 단일 feat:**
```
feat(itinerary): 날짜별 장소 드래그 정렬 추가
```

**Example 3 — refactor with body:**
```
refactor(firestore): places 쿼리를 onSnapshot으로 통합

여러 컴포넌트에서 동일 컬렉션을 중복 구독하던 것을 정리.
한 번만 구독하고 context로 내려보낸다.
```

**Example 4 — 복합 type:**
```
fix,feat(auth): 로그인 흐름 정비

- fix: 만료 토큰 재발급 시 무한 루프 발생하던 문제 수정
- feat: 소셜 로그인 (Kakao) 추가
```

**Example 5 — scope 생략:**
```
chore: tailwind 4.0으로 업그레이드
```

## 자주 빠지는 함정

- **"수정함", "추가했음" 같은 과거형/완료형** → 명령형으로 (`수정`, `추가`)
- **설명 끝 마침표** → 빼기
- **하나의 커밋에 관련 없는 변경 섞기** → stage 단계에서 분리. 의심스러우면 사용자에게 묻는다.
- **type을 일단 `chore`로 도망가기** → 정말 빌드/설정류일 때만. 코드가 바뀌면 `feat`/`fix`/`refactor` 중 하나로.
- **scope을 너무 길게** → `(src/components/ui/dropdown-menu)` ❌ → `(dropdown-menu)` ✓

## 사용자 의사 확인

다음 경우엔 커밋 직전에 한 번 확인을 받는다:
- 작업 트리에 이번 대화와 무관한 변경분이 섞여 있는데 어디까지 커밋할지 애매할 때
- type이 둘 사이에서 진짜 애매할 때 (예: 동작이 살짝 바뀐 refactor — `refactor`인지 `fix`인지)
- 사용자가 평소 영문 커밋 메시지를 쓰는지 한글 커밋 메시지를 쓰는지 직전 커밋들에서 분명하지 않을 때 — `git log --oneline -10`으로 톤을 먼저 본다.

그 외엔 멈추지 말고 바로 커밋한다. 지나친 확인 요청은 흐름을 끊는다.
